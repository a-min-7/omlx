Your scoping is right about decision models, and I would still narrow one word. `/v1/systemone`
and `/v1/decisions` take the decision engine only when the named model is a decision model; for
every other model they go through the ordinary chat path (`_chat_model_decisions` → `engine.chat`),
which is the scheduler the accelerator attaches to, so a readout with a long enough input is split
like any completion. Step 1 is unaffected because it is decision-model-only — the chat-model branch
of those two endpoints is not.

Since then `#5449` has closed the hazard I was pointing at, by construction: `_LORA_CONFLICTS` makes
an adapter and `prefill_helper_node_id` mutually exclusive (with DFlash, VLM MTP, ANE prefill, MoE
offload and external engines), and a merge that carries both keeps the adapter and clears the
accelerator. The reason is the one I raised — the helper runs the targeted projections from the
checkpoint weights, so the delta would be skipped there without notice — and exclusion is a correct
answer to it. I withdraw the warning as an open hazard.

**Q2.** The shipped answer is not the one I would have proposed, and it is better than mine on the
point I cared about. Selection is per loaded model — `lora_adapter` in Model Settings, exposed to
clients as `<model>:<profile>` — and there is no per-request field. `lora_adapter` is part of the
engine's runtime signature, so two adapted variants are not two resident copies of the weights:
switching between arms unloads and reloads. That removes the memory objection I had to the
`<model>:<profile>` route and moves the cost to switching latency.

So the only question left worth answering is whether step 2 still means attaching the adapter to an
already-loaded model, without a reload. If avoiding that reload is the point, per-request selection
returns and the accelerator hazard returns with it — and then "requests that use the adapter stay
local" is the safe first version: no launch handshake, no adapted branch inside the helper, correct
by construction. If it is not the point, `#5449`'s route already covers step 2 and this thread needs
documenting rather than designing.

**Q3.** Under the shipped route there is nothing separate to decide: the picker is in Model Settings >
Advanced. If step 2 lifts the exclusion, its control belongs in the step 2 PR — a knob whose only
consumer is that mechanism has no independent meaning to review.

**What a step-2 branch must be able to show.** With the accelerator enabled and an adapter-requested
prompt of ≥2,048 tokens, one of two things, and it should say which: the request stayed local — no
helper session for it, the host accounting for its tokens — or the helper's status names the adapter
it ran. The middle case, a split with the adapter on one side, must not be reachable by accident,
including from the chat-model branch of `/v1/systemone` and `/v1/decisions`.
