Agreed on both halves, and your scoping is better than my warning was: step 1 answers
`/v1/systemone` and `/v1/decisions` from the decision engine, and the accelerator only ever
attaches to a chat model's engine, so those prompts cannot be split. I checked the same thing
before writing this: on the build I run, the helper is started per engine that exposes one
(`engine_pool.py`, at the model-load path) and nothing in the decision path references it. So
step 1 is unaffected, as you say.

That leaves step 2, where I would order the two outcomes you name: **start with "stay local",
not with "the helper gets the adapter"**, and make that limitation visible rather than silent.

The reason is asymmetry of effort and of proof. The helper is a one-model process: `model_type`
selects the model class at startup, the layer split is fixed at launch, and the job message
carries a token array, chunk sizes, a layer count and a capture window — nothing that could name
an adapter. Giving it one is a launch-handshake change plus shipping the adapter next to the
model, and none of it can be validated until step 2 exists at all. "Requests that use the
adapter stay local" needs no handshake, is safe by construction, and the first version of step 2
is then correct rather than half-adapted. If the split later carries an adapter identity, that
is an optimisation with its own PR.

**Q2 — the request field.** I would take your proposal: an optional `"adapter": "<name>"` on the
request, absent meaning exactly today's behaviour (byte-identical; no fallback guessing). The
alternatives each cost more than they look:

- `model:adapter` creates a second *name* for the same weights. Discovery, admin and the model
  list then have to explain that two entries are one model, and anything keyed on the model name
  — prefix caches above all — starts treating them as two models. That is the opposite of
  step 2's whole argument, which is that there is one copy of the weights.
- A profile reloads the model, so it defeats the memory win.
- Always-on leaves no way to ask the plain model a question in the same process.

The field matches the existing extras (`images`, `truncate`) and is the only one of the four that
can say "this request uses the adapter, that one does not" about a single loaded model.

Three mechanics I would decide in the same PR, because each is a silent-wrong-answer if left:

1. **An unknown or unavailable adapter is a 400, never a fallback to the base model.** A silent
   fallback is indistinguishable from the adapter being ignored, and that is exactly the failure
   a caller would not notice.
2. **The adapter is part of the cache identity.** An adapted and an unadapted request must not
   share a prefix cache entry; with the accelerator on, that has to hold on the host side too.
3. **The response or the log names the arm that served the request.** A row that cannot say
   whether the adapter ran is not evidence, and it is the first thing I would check on a branch.

**Q3 — the dashboard setting.** In the step 2 PR. A setting whose only consumer is step 2's
mechanism has no independent meaning to review; split out, it is a knob for a feature that is
not there yet. Keep it to one decision (attach this adapter to that loaded model, detach it),
and let the validation live in the API so the dashboard and the request path cannot disagree.

**What step 2 should be able to show.** With the accelerator enabled and a prompt of ≥2,048
tokens that requests the adapter, the PR should be able to demonstrate one of two things, and
say which: the request **stayed local** — no helper session for it, the host's own status
accounting for its tokens — or the helper's status **names the adapter it ran**. My warning was
only that the middle case, a split with the adapter on one side, must not be reachable by
accident.

The offer from before stands and is now concrete: once step 2 has a branch, I can run it on a
Qwen3.8-27B oQ4e build across a host+helper split and report which arm served an
adapter-requested long prompt, plus whether staying local costs what you would expect in
latency. I have measured that split on the dense 27B; I have not run a LoRA adapter on either
side, so nothing here is a claim about adapted output.
